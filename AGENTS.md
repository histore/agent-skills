# Workspace Agent Guidelines: Subagent Roles & Context Isolation

## Overview
This workspace employs specialized subagent roles, adaptive execution profiles, and a zero-token deterministic script toolkit with a clear **dual mission**:
1. **Ensure Maximum Engineering & Result Quality** through **Clean Code**, **Clean Architecture**, systematic **Root Cause Analysis (Troubleshooting)**, **Inner-Loop TDD**, two-stage quality gates, and strict security/data-loss guardrails.
2. **Reduce Token & Compute Costs to the Necessary Minimum** through **Compound Phased Execution** (75–90% KV-cache reuse), **Adaptive T-Shirt Sizing** (70–80% fast-track savings), **Calibrated Sweet-Spot Model & Thinking Budgets**, **Zero-Token Script Offloading**, **Context Isolation**, and **Anti-Ceremony Guardrails**.

All skills and rules are designed to be general and reusable across diverse projects. Programming languages, frameworks, libraries, and toolchains are never hardcoded; agents dynamically discover and adapt to the target project's conventions and ecosystem.

## Core Governance & Architecture Rules
1. **Clean Architecture Principles**:
   - Universal separation of concerns across layers (Domain/Entities -> Application/Service Contracts -> Interface Adapters / Presenters / ViewModels -> External Frameworks / UI / Storage / Drivers).
   - Core domain logic and service interfaces must remain strictly agnostic of UI frameworks, databases, and external delivery mechanisms.
2. **Clean Code & Universal Best Practices**:
   - Adhere to SOLID, DRY, KISS, YAGNI, Boy Scout Rule, and clear, descriptive naming conventions.
   - Write clean, idiomatic code adhering to the best practices and type-safety mechanisms of the target project's programming language. In Rust codebases, `unsafe` blocks must not be used.
   - All source code comments and docstrings must be written in English.
   - **Relative Paths Invariant in Documentation**: All file references, links, and paths within documentation, markdown files (`*.md`), specifications, architecture documents, and living feature documents MUST strictly use **relative paths** (e.g. `../ARCHITECTURE.md`, `./features/FEAT-001.md`, `docs/requirements/modules/auth.md`). Absolute local paths (such as `C:\...`, `/home/...`, `/Users/...`, or machine-specific `file:///` URIs) are **strictly prohibited** in committed documentation to guarantee cross-platform portability across different machines, operating systems, and CI runners.
3. **Dynamic Tech Stack Specialization**:
   - Skills do not hardcode programming languages (e.g., C#, Rust, Python, TypeScript, Go) or specific frameworks/libraries (e.g., Avalonia, React, Tokio, ASP.NET).
   - Agents dynamically detect the project stack by inspecting build configurations, package manifests (e.g., `Directory.Build.props`, `Cargo.toml`, `package.json`, `pyproject.toml`, `go.mod`), and the architecture baseline (`ARCHITECTURE.md`).
4. **Core Workflow vs. Domain & Lifecycle Specialists**:
   - **Core Lifecycle Roles** handle the general development lifecycle: `Control`, `RequirementEngineer`, `Architekt`, `Developer`, `Tester`, `Verifikation`, `CommitManager`, `PRManager`.
   - **Default Entry Point & Orchestrator Invariant**: All interactions and user requests across all AI assistants (Google Antigravity, GitHub Copilot, Cursor) MUST start with the `Control` persona (`ask-control`). The agent automatically classifies incoming requests into adaptive execution profiles (Profile 0, A, B, C) and dynamically coordinates downstream roles. In single-thread environments like GitHub Copilot (Sequential Persona Mode), the agent seamlessly transitions personas sequentially (`Control` -> `Developer` -> `Verifikation` -> `CommitManager`) within the conversation thread without requiring the user to invoke `ask-control` manually.
   - **Lifecycle & Domain Specialists** (e.g., `Troubleshooter`, `GitTroubleshooter`, `RefactoringSpecialist`, `ArchitectureSync`, `DocumentationSpecialist`, `DevOpsEngineer`, `CodeReviewer`, `UIDesigner`, `LocalizationSpecialist`, `PerformanceOptimizer`, `SecurityAuditor`, `DatabaseSpecialist`, `ApiContractSpecialist`) are engaged **on-demand**.
   - **On-Demand Specialist Invocation**: Specialists are **NOT** mandatory serial steps on every commit. They are engaged selectively:
     - `Control` includes them when the feature or task explicitly involves that specific domain (e.g., UI layout changes, database migrations, dedicated technical debt audits, changelog releases, architectural drift sync, deep adversarial code review via `CodeReviewer`).
     - Other roles (such as `Developer`, `Architekt`, `Verifikation`, or `Troubleshooter`) can consult or delegate to these specialists to clarify domain-specific nuances, edge cases, and technical constraints.
5. **Automated Testing, Quality & Inner-Loop TDD**:
   - Development follows **Inner-Loop Test-Driven Development (TDD)** (Red-Green-Refactor) adapted to task complexity:
     - **Profile 0 (Direct Response - Informational / Read-Only / Trivial)**: Answer directly. **Zero Git operations and zero test execution.**
     - **Profile A (Fast-Track - Bugs, Tweaks, Small Features)**: Developer authors targeted unit tests and implementation code directly in a single, fast red-green-refactor loop (saving 70–80% latency and token cost). If the change affects only non-executable files (documentation, markdown, text resources, comments) or codebases without test suites, test execution is omitted.
     - **Profile B (Standard Features)**: Architecture contract established -> Developer implements unit tests and code via Inner-Loop TDD -> Verifikation quality gate.
     - **Profile C (Complex / Architectural)**: Modular architecture contracts -> Optional skeleton stubs for parallel decoupling -> Comprehensive integration test suites by `Tester` -> Developer implementation.
   - **Purpose-Driven Test Execution**: Tests and test runners must **ONLY** be executed when executable production code has been modified and relevant automated tests exist or need to be authored. Do NOT run test suites for documentation, markdown files, comments, static text assets, simple scripts without test suites, or when tests are unrelated to the edited file.
   - **Targeted Test Execution**: During inner loops, test runners must target only the affected test file or class (`dotnet test --filter`, `cargo test <name>`, `npm test -- <path>`, `pytest <path>`), executing the full test suite once during final verification to avoid full-suite build thrashing.
   - **Two-Stage Quality Gate (Shift-Left Validation)**:
     - **Stage 1 (Deterministic Fast-Gate - Zero Tokens)**: Native build (`dotnet build`, `cargo check`), project linter, and quiet native test runner (0 errors, 100% pass). If failing, immediately return for remediation without consuming LLM tokens on semantic analysis. Only triggered when testable code changes were made.
     - **Stage 2 (Concise Traceability Gate)**: `Verifikation` audits acceptance criteria fulfillment, Clean Architecture boundaries, and logical correctness (with optional deep adversarial inspection via `CodeReviewer`).
   - **Test Integrity Guardrail**: Replaces rigid test immutability. The Developer is empowered to adjust and refine test fixtures, signatures, and assertions to match real contracts and idiomatic types. Weakening, bypassing, or deleting assertions to fake passing tests is strictly forbidden.
   - **Circuit Breaker**: The `Developer`'s targeted test-fix feedback loop is capped at a maximum of 3 iterations before escalating.
   - **Comprehensive Scenario Coverage**: Unit and integration tests follow the Arrange-Act-Assert (AAA) pattern.
   - Automated test execution relies on the project's native test runner, requiring a 100% pass rate with 0 failures before verification sign-off when tests are applicable.
   - **Synthetic Evaluation Suite (Eval-Harness)**: Governance rules, execution profiles, anti-ceremony boundaries, safe-Rust invariants, and circuit-breaker behaviors are continuously asserted via `evals/eval-cases.json` and `scripts/run-evals.ps1` (`run-evals.sh`).
6. **Internationalization & Localization (i18n / l10n)**:
   - When user-facing interfaces are present, maintain 0% hardcoded user strings; manage texts in structured bilingual resources in **German (`de`)** and **English (`en`)** using the project's native localization format.
7. **Requirements Governance & Modular Architecture**:
   - **Consistency & Deduplication**: All new requirements must be validated against existing requirements.
   - **Single-File vs. Modular Hub-and-Spoke Scaling**:
     - *Single-File (`REQUIREMENTS.md`)*: Suitable for small, focused projects or initial phases (< ~30–50 requirements).
     - *Modular Architecture (`docs/requirements/modules/<module>.md`)*: When a project scales, exceeds ~30–50 requirements, or aligns with modular architecture (`docs/architecture/modules/*.md`), requirements must be segmented into per-module files. The root `REQUIREMENTS.md` acts as the central **Hub, Index, ID Registry, and Non-Functional Requirements (NFR) Baseline**.
   - **Living Modular Documentation & Phased Feature Specs**:
     - *Append-Only / Delta Growth*: Specifications must never be generated or mutated as one monolithic block. Living documentation grows step-by-step as isolated feature documents (`docs/features/FEAT-<SCOPE>-XXX-<slug>.md` or `docs/requirements/modules/<module>.md`).
     - *Zero-Full-Diff Guarantee*: Changes and new features only affect the targeted feature file and add a single link row to the central Hub index (`docs/ROADMAP.md` or `REQUIREMENTS.md`), avoiding multi-page diffs and merge conflicts.
     - *Phase-Driven Progression*: Features are mapped to explicit implementation phases (`phase: 1`, `phase: 2`, etc.) and lifecycle states (`PROPOSED`, `APPROVED`, `IN_PROGRESS`, `IMPLEMENTED`, `VERIFIED`), enabling clean phase-by-phase execution without cognitive overload.
     - *Lazy Loading & Token-Hygiene Protocol (Zero Full-Parse Invariant)*: On subsequent runs or turns, agents and tools MUST NOT read or parse all specification files. They read only the central Hub index (`docs/ROADMAP.md` / `REQUIREMENTS.md` registry), identify the target feature for the active task/phase, and load strictly that single file into context (saving 80–95% context tokens).
     - *Zero-Token Offloading Scripts*: Inspect features, filter by phase, check drift, and scaffold new templates without LLM token cost via `scripts/inspect-feature-specs.ps1` (`inspect-feature-specs.sh`) and `scripts/lint-requirements.ps1` (`lint-requirements.sh`).
   - **Namespaced Requirement IDs**: Each requirement must follow a unique scoped ID pattern: `REQ-<SCOPE>-XXX` (e.g. `REQ-AUTH-001`, `REQ-CORE-002`, `REQ-UI-003`).
   - **Lifecycle Status Tracking**: Every requirement tracks an explicit state (`PROPOSED`, `APPROVED`, `IMPLEMENTED`, `VERIFIED`, `DEPRECATED`).
   - **Context Isolation for Downstream Agents**: When assigning tasks to subagents (`Developer`, `Tester`, `Verifikation`), pass only the central index and the specific affected module requirement file (`docs/requirements/modules/<module>.md`) to maintain strict context hygiene and prevent token bloat.
8. **User Decision on Conflicts**: In case of contradictions or duplicates, the user must make the decision.
9. **Immutability of Existing Requirements**: Existing requirements may only be modified with explicit user instruction.
10. **100% Coverage for Functional Features**: 100% of newly introduced functional features in Enterprise mode must be covered by approved requirements. Trivial bug fixes, minor tweaks, refactorings, documentation updates, and prototype work do not require bureaucratic requirement documentation.
11. **Dynamic Model Allocation & Universal Execution Strategy**:
    - Model tiers, model classes, and execution modes are declaratively defined in [`rules/model-tiers.json`](rules/model-tiers.json).
    - **Task-Complexity-Driven Model Allocation (Dynamic Right-Sizing into 3 Classes)**:
      - **ECO**: Auto-allocated for Profile 0 & Profile A (trivial requests, bugfixes, docs, scripts, Tier 4 Git/lifecycle). Auto-approved, runs on lightweight models (`flash`, `gpt-4o-mini`, `claude-haiku`) with minimal reasoning to minimize token consumption.
      - **BALANCED**: Auto-allocated for Profile B (standard feature engineering, unit tests, Clean Code inner-loop TDD). Auto-approved sweet spot balancing cognitive depth and quota usage (`inherit`, `sonnet`, `flash` with medium reasoning).
      - **PREMIUM**: Allocated for Profile C (complex architectural redesigns, cross-module refactorings, deep deadlocks, security audits). **Subject to Mandatory Quota Protection User Gate**.
    - **Quota Protection User Gate**: Whenever an incoming task is classified as Profile C / Premium, `Control` pauses execution before consuming quota and presents an immediate 3-class selection (`[1] Premium`, `[2] Balanced`, `[3] Eco`) to the user. Direct selection or prompt parameterization (e.g. `--eco`, `--balanced`, `--premium`, or direct prompt instruction) satisfies the gate immediately. In multi-agent environments (Antigravity), this renders as an interactive prompt/modal; in single-model environments (Copilot), it outputs an explicit recommendation gate in chat and modulates the prompt/thinking budget.
    - **Cost-Efficiency & Sweet-Spot Policy (Calibrated Model Allocation)**: Agents, subagents, and skills must always hit the "sweet spot" balancing cognitive capability and cost-efficiency. Avoid wasteful over-provisioning (e.g., flagship models for trivial file searches, simple diffs, or repetitive formatting) as well as destructive under-provisioning (e.g., starving complex architectural, diagnostic, or security tasks with underpowered models that produce hallucinations, broken abstractions, or repetitive TDD test failures). Subagents invoked via `invoke_subagent` default to `inherit` to maintain the fidelity of the active session without artificial downgrades. Divergent exploratory research uses lightweight models (`flash`). Deterministic lifecycle actions (commits, PR manifests, release tags) use fast, reliable models (`flash`), strictly avoiding underpowered tiers (`flash_lite`) that fail at structured output. Strategic and diagnostic roles (`Troubleshooter`, `Architekt`, `CodeReviewer`, `SecurityAuditor`) leverage high reasoning or flagship models (`pro` / high reasoning) when task complexity (Profile C) or deadlock resolution demands it.
    - **Compound Phased Execution & Zero-Reload Invariant (Default Strategy)**: Core development workflows (Plan -> Inner-Loop TDD -> Verify -> Commit) execute within a **continuous conversation thread** via phased persona transitions. This preserves prefix continuity, unlocking **75–90% prompt caching / KV-cache discounts** and eliminating multi-agent spawn latency.
      - **Zero-Reload Core Role Cheat-Sheet**: For Profile 0, Profile A, and standard Profile B tasks, the operational rules for `Architekt` (Clean Architecture inward dependencies, modular contracts), `Developer` (Inner-Loop TDD, quiet targeted tests, max 3-iteration circuit breaker, no `unsafe` in Rust, English comments), `Verifikation` (single-command Stage-1 `run-fast-gate.ps1` + Stage-2 acceptance/boundary check), and `CommitManager` (atomic commits, submodule isolation, conventional commits) are already present in this baseline. **Do NOT waste tool calls reading `ask-developer/SKILL.md`, `ask-verification/SKILL.md`, or `ask-commit-manager/SKILL.md` during standard compound execution.** Read individual `SKILL.md` files strictly when invoking On-Demand Specialists or resolving complex anomalies.
      - **Zero-Probe Environment Detection**: Determine your execution environment (`multi_agent` if `invoke_subagent` tool is present, otherwise `sequential_persona`) directly from your active tool declarations. Do **NOT** spend a terminal tool call executing `detect-models.ps1` during normal task workflows unless explicitly diagnosing model catalogs.
    - **Selective Subagent Forking (`invoke_subagent`)**: Reserved strictly for **divergent research**, broad multi-file repository exploration, web lookups, or independent background sidecars to keep exploratory token noise out of the primary thread. Dispatch `research` subagents with `Model: "flash"` (ECO class) to conserve flagship quota.
    - **Terminal & Context Hygiene**: All PowerShell commands must use `-NoProfile`. Testrunners must run in quiet mode (`dotnet test --verbosity quiet`, `cargo test -q`, `pytest -q`) to prevent terminal logs from bloating the context window.
    - **Sequential Persona Mode (Copilot / Cursor / Single-Model)**: Uses prompt-modulated thinking budgets (Extended for Tier 1, Low/Minimal for Tier 3/4). In GitHub Copilot, the single-agent thread dynamically switches personas sequentially: `Control` (sizing & planning) -> (`RequirementEngineer`/`Architekt`) -> `Developer` (Inner-Loop TDD) -> `Verifikation` (quality gate) -> `CommitManager`. Transitions are explicitly labeled in the conversation output (e.g. `### [Phase: Control]`).
    - **Cost-Guardrail (Budget Protection Circuit Breaker)**: Prevents accidental budget-burning when high-cost flagship models (> $4.00/M input, > $20.00/M output, e.g. GPT-6 Astra, Claude Opus, Claude Fable) are active during routine, mechanical, or repetitive operations. In multi-agent environments, subagents for Tier 4 (Commits/PRs) or divergent searches automatically throttle to cost-efficient models. In sequential/single-model environments (Copilot), a Smart Confirmation Gate pauses execution and recommends switching to the Daily Driver (Gemini Flash / GPT-6.1 Sol / Luna) before consuming large token volumes on routine tasks, unless explicitly confirmed by the user.
    - **Zero-Overhead Lifecycle Telemetry & Observability**: Phase transitions, durations, and execution events can be recorded locally via `scripts/record-telemetry.ps1` (`record-telemetry.sh`) and inspected via `scripts/show-telemetry.ps1` (`show-telemetry.sh`) without consuming LLM tokens.
12. **Branch & PR Process Model with Developer Testing & Review Gate**: All development must occur on dedicated branches (`feat/`, `fix/`, `refactor/`, `chore/`, `docs/`). Prior to Pull Request creation, the developer is provided with the opportunity to review the code, test application functionality interactively/manually, and request adjustments or fixes. Merging into `main` occurs solely via Pull Requests using Squash-and-Merge after explicit user sign-off and passing CI per [CONTRIBUTING.md](CONTRIBUTING.md).
    - **Purpose-Bound Git Operations**: Git status checks, branch creation, or checkout commands must **ONLY** be executed when changes are actively being committed or pushed, or when explicitly requested by the user. Do **NOT** invoke git commands proactively during read-only queries or local edits.
13. **Four-Step Codebase Analysis Protocol**:
    When exploring, analyzing, or diagnosing a codebase for structural or architectural tasks, agents must strictly follow four progressive steps:
    1. **Check Current Modular Architecture Baseline**: Verify `ARCHITECTURE.md`, module specifications (`docs/architecture/modules/*.md`), and state checkpoint (`.arch-sync.json`).
    2. **Synchronize Architecture if Needed**: If the documentation is missing, outdated, or desynchronized from recent git commits, trigger `ArchitectureSync` to update affected module documents.
    3. **Deduce State from Modular Architecture Documentation**: Derive component responsibilities, public contracts, data flows, and runtime state directly from the relevant modular architecture specification (`docs/architecture/modules/<module>.md`).
    4. **Targeted Code Inspection Only for Critical Details**: Read concrete source code files strictly when specific low-level implementation details (e.g. algorithmic nuance, interop declarations, exact event routing lines) are indispensable.
    **Pragmatic Bypass**: For localized questions, simple queries, or isolated bugfixes within a single known file, bypass this multi-step protocol and inspect the relevant file directly without checking git deltas or architecture synchronizations.
14. **Lifecycle Action Execution Governance (Commit, Push, PR Merge, Release)**:
    Defined Git and release actions adhere to seven explicit execution principles:
    1. **Strict Action Execution (Atomic Scope)**: When the user requests a specific action (e.g. `commit`), execute only that action (e.g. commit only, do not automatically push).
    2. **State-Driven Prerequisite Resolution**: If the requested action requires preceding steps based on the current workspace or repository state (e.g. uncommitted changes present when `push` is requested), automatically resolve the necessary prerequisites first.
    3. **Proactive Next-Step Offering**: When an action completes and a logical subsequent step is derivable, proactively offer the user to execute it directly.
    4. **Adaptive Gate Resolution (Intention Matching with Anomaly Fallback)**: When the user's prompt directly instructs or parameterizes an action (e.g. "erstelle einen minor release", "commit with message ..."), the review/confirmation gate is satisfied by the prompt and executes directly without redundant re-confirmation. However, an interactive confirmation gate remains mandatory and pauses execution if: (a) uncommitted/untracked changes exceed the task's scope, (b) SemVer rules in commit history contradict the requested release bump (e.g. breaking changes detected on a minor request), (c) branch protection/quality gates are violated, or (d) an atypical repository state occurs.
    5. **Explicit User Override**: The user may explicitly instruct deviating or combined behavior at any time (e.g. "commit and push directly").
    6. **Atypical State & Anomaly Gate**: If following these instructions would produce an unusual state or require non-standard/atypical measures (e.g. detached HEAD, merge conflicts, unexpected untracked files, unverified release states, cross-cutting multi-scope changes), the agent must pause, describe the situation, and prompt the user for explicit confirmation before proceeding.
    7. **Clean Release Tagging Invariant**: Release tags (`vX.Y.Z`) must be applied directly to the existing production/merge commit on `main`. Standalone metadata commits (such as `docs(changelog): release v...`) directly on `main` during release tagging are strictly prohibited to maintain an uncluttered Git commit history focused on actual functional changes. Release notes belong in tag annotations or GitHub Releases.
15. **Adaptive Governance & Strictness Levels**:
    - To prevent architectural overhead on small or legacy tasks, `Control` must establish and propagate a `Strictness Level` context:
      - **Standard (Default)**: Task-proportional and purpose-driven. Applies Clean Code and targeted tests where applicable; strictly avoids ceremonial overhead (e.g. running test suites on documentation, proactive git status calls on read-only queries, requirement registration for trivial tweaks).
      - **Enterprise**: Strict formal adherence to Clean Architecture, 100% test coverage, and full Requirement mapping for substantial features and critical modules when explicitly requested or required by repository governance.
      - **Legacy**: Tolerates architectural deviations and missing tests (does not block verification), but requires Stage 1 compilation success.
      - **Prototype**: Focuses on speed (MVP). Architecture documentation and TDD are strictly optional.
16. **Purpose-Driven Execution & Anti-Ceremony Guardrail (No Process for Process's Sake)**:
    - All actions, checks, and tool invocations must serve a tangible, practical purpose for the user's specific request. Steps must **NEVER** be executed merely to satisfy formal process definitions, checklists, or pipelines if they have no functional value for the task at hand:
      - **Informational & Read-Only Requests**: When the user asks a question, requests an explanation, code review, or exploratory analysis, agents must **NEVER** run git checks (`git status`, `git branch`), test runners, or architecture synchronization. Answer directly and concisely.
      - **Purpose-Bound Git Operations**: Git commands (`git status`, branch switching, etc.) are strictly forbidden unless a git-persisted action (commit, push, branch creation, PR) is actively being executed or explicitly requested by the user. Do not check git status proactively during simple file edits.
      - **Context-Relevant Testing**: Test runners and compilation gates are executed strictly when executable production code has been modified and relevant automated tests exist or need to be authored. Do NOT run test suites for documentation, markdown files, comments, static text assets, simple scripts without test suites, or when tests are unrelated to the edited file.
      - **Lightweight Trivial Changes**: Bug fixes, minor tweaks, configuration adjustments, and refactorings do not require bureaucratic upfront ceremonies (e.g. creating formal `REQ-` entries or checking `.arch-sync.json` drift) unless explicitly requested or when architectural boundaries are structurally changed.

## Subagent Roles & Governance Mappings
All 23 specialized subagent roles, their cognitive tiers, reference models, and thinking budgets are declaratively maintained in the Single Source of Truth: [`rules/model-tiers.json`](rules/model-tiers.json).
- **Core Lifecycle Roles**: `Control`, `RequirementEngineer`, `Architekt`, `Developer`, `Tester`, `Verifikation`, `CommitManager`, `PRManager`.
- **Lifecycle Specialists (On-Demand)**: `Troubleshooter`, `GitTroubleshooter`, `CodeExplainer`, `RefactoringSpecialist`, `DocumentationSpecialist`, `ArchitectureSync`, `DevOpsEngineer`, `ReleaseManager`, `CodeReviewer`.
- **Domain Specialists (On-Demand)**: `UIDesigner`, `LocalizationSpecialist`, `PerformanceOptimizer`, `SecurityAuditor`, `DatabaseSpecialist`, `ApiContractSpecialist`.

Operational execution instructions are defined exclusively in each role's skill specification in [`skills/`](skills/).

## Context Isolation & Compaction Protocol
- Subagents must be called with only the minimum context required for their specific role.
- Intermediate results (e.g. root cause reports, UX blueprints, i18n dictionaries, architecture contracts, diffs, acceptance criteria) are passed downstream sequentially.
- No role shall receive bloated discussion history or unrelated files.
- **Proactive Context Compaction & Phase Checkpointing**:
  - To prevent "Lost in the Middle" degradation and trim token bloat, `Control` executes explicit context compaction at major phase boundaries (e.g., Plan -> Implementation, or between distinct user tasks).
  - Before transitioning or starting a new task, synthesize a concise **State Checkpoint** (active goal, touched files, verified architecture facts, next concrete steps).
  - Discard obsolete intermediate trial-and-error logs, failed compilation attempts, and transient conversation history, while strictly preserving top-of-context system rules to maximize KV-cache prefix hits.

## Client Directory Compatibility (`.agents` vs. `_agents`)
- **Gemini / Antigravity**: Uses `_agents` as the standard customization root (keeping `.agents` available for repository-specific customizations).
- **GitHub Copilot & Other Clients**: Specifically expect `.agents/` as the standard discovery root. When sharing skills across multiple AI clients or targeting Copilot, use `.agents` (or create a symbolic link / submodule pointing to `.agents`).

Detailed skill definitions can be found in `skills/` (or `_agents/skills/` / `.agents/skills/` when consumed as a submodule) and rules in `rules/` (or `_agents/rules/` / `.agents/rules/`).
